# 기능 설계 계획 — U3 v2-server

**유닛**: v2-server (Node.js + TypeScript, 계층형) + V1 UI 재사용 클라이언트
**담당 스토리**: US-DOC-7(서버 상태 공유), US-MGR-3(과별 진행 취합), (재사용) US-OP/DOC/MGR 공통

## 질문 1 — 진행 상태 저장 백엔드
V2에서 진행 상태를 어디에 저장할까요? (프로토타입/로컬 실행 전제)

A) JSON 파일 (서버 로컬 파일에 상태 맵 저장) — 의존 없음, 설정 제로, 학습에 투명

B) SQLite (내장 파일 DB) — 표준적이나 드라이버 의존/스키마 추가

C) 인메모리 (재시작 시 초기화) — 가장 단순하나 영속성 없음(공유 데모용)

X) 기타 (아래 [Answer]: 뒤에 설명해 주세요)

> 🤖 **백엔드 엔지니어 권장**: A) JSON 파일
> **근거**: 각 보기 검토 — 저장 대상이 noteId→상태 맵으로 구조가 단순하고 소량(수백 건)이라 A로 충분하며, 외부 DB 의존/드라이버/스키마 없이 파일 하나로 영속성(FR-V2-1)과 다중 사용자 공유(같은 서버 파일 참조)를 만족하고 학습자가 저장 내용을 파일로 바로 볼 수 있음. B(SQLite)는 관계형이 필요할 때 이점이나 이 데이터엔 과하고 네이티브 드라이버 설치 이슈 가능. C(인메모리)는 재시작 시 소실되어 "공유·유지"(US-DOC-7) 요구를 부분만 충족.
> **숙고 포인트**: (트레이드오프) A는 동시 쓰기 시 파일 경합 가능 — 소규모/저빈도라 쓰기 직렬화(간단한 순차 저장)로 충분. / (되돌리기) StatusRepository 계약 뒤에 있어 후에 B로 교체 쉬움. / (다른 선택이 유리한 경우) 조회/집계가 복잡해지거나 동시성이 높아지면 B.
> **신뢰도**: High

> 🤖 **소프트웨어 아키텍트 권장**: A) JSON 파일 (StatusRepository 뒤에 격리)
> **근거**: 저장 방식을 Repository 계층에 격리했으므로(앱설계 Q3=A) 백엔드 선택은 국소적 결정. A가 프로토타입·학습 목적에 가장 단순하고, 계약이 동일해 V1(localStorage)·V2(파일)가 대칭적이라 설명이 쉬움. B/C는 각각 과설계/비영속.
> **숙고 포인트**: (되돌리기) 교체 지점이 Repository 하나라 리스크 낮음. / (먼저 확인) 서버 재시작·배포 시 파일 경로 유지 여부. / (다른 선택) 운영 전환 시 관리형 DB로 승격 고려(범위 밖).
> **신뢰도**: High
