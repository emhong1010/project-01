## 질문 1 — 공통 코어(shared-core)의 컴포넌트 분해
파싱/판별/집계를 담당하는 공통 코어를 어떤 컴포넌트로 나눌까요?

A) 기능별 분리: `FileParser`(CSV/Excel 파싱) · `NoteFilter`(판독문 필터) · `FollowUpDetector`(추적관찰 판별+근거/시점 추출) · `DepartmentAggregator`(과별 집계)

B) 단계 파이프라인 하나로 통합: `ReportProcessor` 하나가 파싱→필터→판별→집계를 순차 처리 (내부 함수로만 분리)

C) 최소 분리: `Parser` + `Analyzer`(필터+판별+집계 통합) 2개

X) 기타 (아래 [Answer]: 뒤에 설명해 주세요)

> 🤖 **소프트웨어 아키텍트 권장**: A) 기능별 분리
> **근거**: 각 보기 검토 — A는 파싱/필터/판별/집계를 단일 책임 컴포넌트로 나눠 응집도가 높고, 판별 규칙(가장 자주 바뀔 부분, NFR-4)이 `FollowUpDetector`에 격리되어 변경 영향이 국소적이며 학습자가 구조를 이해하기 쉬움(NFR-6). B는 한 클래스에 4관심사가 묶여 규칙 수정 시 전체를 건드리고 테스트 격리가 어려움. C는 Analyzer가 필터·판별·집계를 겸해 판별 로직 테스트와 재사용이 애매. 코어 재사용(NFR-7)·규칙 집중화 요구에 A가 정합적.
> **숙고 포인트**: (트레이드오프) A는 컴포넌트가 늘어 초기 파일 수가 많아지나 각 파일이 작고 명확. / (되돌리기) 판별기를 처음부터 독립시키면 이후 규칙 확장/AI 보완(범위 밖이지만 향후) 시 교체가 쉬움. / (다른 선택이 유리한 경우) 로직이 극히 단순하면 C로도 충분.
> **신뢰도**: High

> 🤖 **백엔드 엔지니어 권장**: A) 기능별 분리
> **근거**: 판별기(`FollowUpDetector`)를 순수 함수 형태의 독립 컴포넌트로 두면 오탐 방지 케이스([임상정보] 제외 등)를 입력→출력으로 단위 테스트하기 쉬움. 파서는 파일 포맷 관심사만, 집계는 과별 그룹핑만 담당해 데이터 흐름이 명확. B/C는 판별 검증 지점이 흐려짐.
> **숙고 포인트**: (트레이드오프) A는 컴포넌트 간 데이터 모델(레코드→판별결과)을 명시적으로 정의해야 함(장점이기도 함). / (먼저 확인) 근거/시점 추출을 판별기 안에 둘지 별도 컴포넌트로 뺄지 — 이번엔 판별기 내부로 두는 것을 권장. / (다른 선택) 성능 극한 최적화가 필요하면 파이프라인 통합(B) 고려(현재 불필요).
> **신뢰도**: Medium

[Answer]: a

## 질문 2 — 공통 코어의 배포/재사용 형태
V1(브라우저)과 V2(Node 서버)가 shared-core를 어떻게 재사용할까요?

A) 플랫폼 독립 TypeScript 모듈로 작성(브라우저/Node 양쪽에서 import) — 파일 I/O·저장은 코어 밖(각 버전)에서 담당하고, 코어는 순수 로직만

B) 코어가 파일 읽기까지 담당(Node용) + 브라우저용 별도 래퍼

X) 기타 (아래 [Answer]: 뒤에 설명해 주세요)

> 🤖 **소프트웨어 아키텍트 권장**: A) 플랫폼 독립 순수 로직 모듈
> **근거**: 각 보기 검토 — A는 코어가 "문자열/데이터 입력 → 판별 결과 출력"의 순수 로직만 담당하고 환경 의존(파일 읽기, localStorage, DB)은 각 버전이 어댑터로 처리 → 코어를 브라우저·Node가 동일하게 재사용(NFR-7)하고 테스트도 환경 없이 가능. B는 코어에 Node 파일 API가 섞여 브라우저에서 그대로 못 써 재사용 목표가 깨지고 래퍼 중복 발생.
> **숙고 포인트**: (되돌리기 어려움) 코어에 환경 의존을 넣으면 두 버전 재사용이 불가능해져 근본 재설계 필요 — 초기에 순수성 유지가 중요. / (트레이드오프) A는 각 버전이 입력을 코어에 넘기는 얇은 어댑터를 각각 작성해야 함(작은 비용). / (먼저 확인) Excel 파싱 라이브러리가 브라우저/Node 양쪽 동작하는지 확인 필요.
> **신뢰도**: High

[Answer]: a

## 질문 3 — V2 서버 아키텍처 스타일
V2 서버(Node.js + TypeScript)의 계층 구조를 어떻게 잡을까요?

A) 단순 계층형: 라우터(REST) → 서비스 → 저장소(Repository) → 데이터 저장. shared-core는 서비스가 호출

B) 미니멀: 라우터에서 바로 로직·저장 처리(계층 최소화, 가장 빠른 구현)

X) 기타 (아래 [Answer]: 뒤에 설명해 주세요)

> 🤖 **소프트웨어 아키텍트 권장**: A) 단순 계층형(라우터→서비스→저장소)
> **근거**: 각 보기 검토 — A는 진행 상태 저장(Repository)을 교체 가능한 계층으로 분리해 저장 방식(파일/경량 DB) 변경이 쉽고, 학습자가 "요청이 계층을 따라 흐르는" 전형적 구조를 배우기 좋음(NFR-6). B는 초기 구현은 빠르나 라우터에 로직·I/O가 섞여 테스트·확장·설명이 어려움. 프로토타입이라도 계층이 3개뿐이라 A의 오버헤드가 작음.
> **숙고 포인트**: (트레이드오프) A는 파일 2~3개가 더 생기나 각 역할이 명확. / (다른 선택이 유리한 경우) 정말 즉석 데모만 목표면 B. / (먼저 확인) 저장 백엔드(파일 JSON vs SQLite 등) 선택은 기능 설계에서 확정 예정.
> **신뢰도**: Medium

[Answer]: a

## 질문 4 — V1/V2 프론트엔드 UI 공유
V1과 V2의 화면(업로드·대시보드·과 탭·표·상태 변경 UI)을 어떻게 처리할까요?

A) UI 컴포넌트도 최대한 공유 — 데이터/상태 소스(localStorage vs 서버 API)만 주입 방식으로 교체

B) V1 UI를 먼저 만들고, V2는 V1 UI를 재사용하되 상태 저장만 서버 연동으로 교체

C) 각각 독립 UI로 단순하게 (공유 안 함) — 학습 시 두 버전을 따로 보기 쉬움

X) 기타 (아래 [Answer]: 뒤에 설명해 주세요)

> 🤖 **프론트엔드 엔지니어 권장**: B) V1 UI 먼저 → V2가 재사용, 저장 계층만 교체
> **근거**: 각 보기 검토(구현/학습 관점) — B는 화면 컴포넌트를 재사용해 중복을 줄이면서도, 데이터 접근을 "저장소 어댑터(localStorage / fetch API)"로 추상화해 교체 지점이 한 곳으로 명확 → 상태 로컬성 유지·학습 설명 용이. A는 이상적이나 처음부터 완전 추상화하면 프로토타입에 과설계. C는 공유가 없어 규칙/화면 수정 시 두 곳을 고쳐야 하고 불일치 위험.
> **숙고 포인트**: (트레이드오프) B는 V1 설계 시 "저장소 인터페이스"를 미리 염두에 둬야 함(작은 선투자). / (되돌리기) C로 가면 나중에 공유로 합치는 비용이 큼. / (참고: 사용자 흐름/UX 세부는 제품 책임자 영역) 화면 흐름 자체의 적절성은 스토리(US-*) 기준으로 이미 정의됨.
> **신뢰도**: Medium

[Answer]: b
