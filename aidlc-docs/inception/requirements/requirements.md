# 요구사항 명세서

## 1. 의도 분석 요약

- **사용자 요청**: "판독문에서 추적 관찰이 필요한 건을 찾아 목록으로 보여주는 도구를 만들어줘." + 추가 요구("진료과별 대시보드/표 분리", "각 과 선생님이 진행 상황 표기")
- **요청 유형**: 신규 프로젝트 (Greenfield)
- **범위 추정**: 다중 컴포넌트 (공통 코어 + V1 웹 + V2 서버)
- **복잡도 추정**: 보통 (규칙 기반 판별 + 과별 대시보드 + 진행 상태 관리, 2버전)
- **도메인**: 의료 (영상의학 판독문 텍스트 처리)
- **전달 전략**: 2버전 단계적 전달 — V1(서버리스 MVP) → V2(서버 기반 최종형)

## 3. 입력 데이터 계약 (참고 CSV `clinical_notes.csv` 기준)

- **열 구성**: `note_id, note_type, note_date, dept, modality, body_part, author_role, text`
  - `note_id`: 레코드 식별자
  - `note_type`: 기록 종류 (`판독문`, `간호기록`, `경과기록` 혼재)
  - `note_date`: 작성일 (YYYY-MM-DD)
  - `dept`: 진료과 (과 구분 기준)
  - `modality`: 검사 종류 (CT/MR/CR 등)
  - `body_part`: 검사 부위
  - `author_role`: 작성자 역할
  - `text`: 본문. `[검사] / [임상정보] / [소견] / [결론]` 섹션 구조. 쉼표·줄바꿈 포함(따옴표로 감싼 다중행 필드).
- **필수 처리**: `note_type == "판독문"` 인 행만 분석 대상으로 필터링.
- **주의**: `text` 필드에 환자명·연락처·생년월일·등록번호 등 개인정보(PII)가 섞여 있음. 프로토타입/클라이언트 처리 전제상 별도 마스킹은 범위 밖(운영 전 보안 검토 필요).

## 4. 기능 요구사항 (Functional Requirements)

### 공통 (V1/V2 공유 코어)
- **FR-1 파일 업로드/파싱**: 브라우저에서 CSV 또는 Excel(.xlsx)을 업로드하고, 쉼표·줄바꿈이 포함된 따옴표 필드를 올바르게 파싱한다(정식 CSV 파서 사용).
- **FR-2 판독문 필터링**: `note_type == "판독문"` 행만 대상으로 한다.
- **FR-3 추적 관찰 판별(규칙 기반)**: 각 판독문의 `[소견]/[결론]` 텍스트에서 다음과 같은 표현을 탐지해 "추적 관찰 필요"로 판별한다.
  - 양성 신호(예): "추적 검사(를) 권고", "추적 관찰", "추적관찰", "추시", "추가 검사 권고", "추가 평가 권고", "재검이 필요", "재검사", "f/u", "follow up", "follow-up".
  - **오탐 방지**: `[임상정보]` 섹션의 "추적 검사"(= 이번 검사가 추적검사였다는 사유)는 판별 근거에서 제외한다. 부정 표현("불필요", "필요 없음")도 제외한다.
  - 판별 규칙(키워드/패턴)은 코드 한 곳에 모아 쉽게 추가·수정 가능해야 한다(NFR-4).
- **FR-4 근거 추출**: 판별 근거가 된 문장/키워드를 추출해 함께 제공한다.
- **FR-5 추적 시점/기간 추출**: 본문에 권고 시점/기간(예: "3개월 후", "6개월 뒤", "1년 후")이 있으면 추출하고, 없으면 공란으로 둔다.
- **FR-6 메타 표시**: 검사 종류(`modality`)·부위(`body_part`)·진료과(`dept`)·작성일(`note_date`)을 함께 제공한다.

### UI/대시보드
- **FR-7 과별 구분**: `dept` 값 기준으로 데이터를 진료과별로 그룹화한다.
- **FR-8 전체 요약 대시보드**: 상단에 전체 판독문 수, 추적 관찰 필요 총 건수, **과별 추적 관찰 필요 건수(합계)**를 표시한다.
- **FR-9 과 선택 탭**: 과 선택 탭(또는 드롭다운)으로 특정 과를 선택하면 해당 과의 대시보드/표로 전환된다.
- **FR-10 목록 표시**: 선택된 과(또는 전체)의 "추적 관찰 필요" 건을 표로 표시한다. 표 열: 식별자(`note_id`), 진행 상태, 근거 문장/키워드, 추적 시점/기간, 검사 종류/부위, 작성일, 원문(요약 표시 + 펼치기).
- **FR-11 진행 상태 표기**: 각 건의 진행 상태를 대기/진행중/완료 중에서 선택·변경할 수 있다(기본값 대기). 과별 대시보드/표에서 상태를 확인할 수 있다.
- **FR-12 빈/오류 처리**: 파일이 비었거나 형식 오류, 필수 열(`note_type`,`dept`,`text`) 누락 시 사용자에게 명확한 메시지를 표시한다.

### V1 (서버리스 MVP)
- **FR-V1-1 로컬 저장**: 진행 상태 표기 결과를 브라우저 localStorage에 저장하여 새로고침해도 유지한다(단일 브라우저 한정).
- **FR-V1-2 간단 배포**: 정적 파일 호스팅으로 배포 가능해야 한다(서버 불필요).

### V2 (서버 기반 최종형)
- **FR-V2-1 서버 저장/공유**: 진행 상태를 백엔드 + DB에 저장하여 여러 사용자가 공유·갱신할 수 있다.
- **FR-V2-2 사용자 식별**: 접속 시 이름/과를 선택하며(로그인 없음), 상태 변경 시 "누가" 변경했는지 최소 기록을 남긴다.
- **FR-V2-3 API 제공**: 프론트엔드가 호출하는 REST API(판독문 목록/판별 결과 조회, 진행 상태 갱신)를 제공한다.

## 5. 비기능 요구사항 (Non-Functional Requirements)

- **NFR-1 사용성**: 한국어 UI. V1은 설치·서버 없이 브라우저에서 즉시 사용.
- **NFR-2 성능**: 수백 건(샘플 306건)을 체감상 즉시 처리.
- **NFR-3 프라이버시(참고)**: V1은 모든 처리를 브라우저 내에서 수행하고 데이터를 외부로 전송하지 않음. 본문 PII는 프로토타입 범위상 별도 처리하지 않음(운영 전 보안 검토 필요).
- **NFR-4 유지보수성**: 추적 관찰 판별 규칙(키워드/패턴)을 공통 코어의 한 곳에 모아 관리.
- **NFR-5 정확성(참고)**: 규칙 기반 한계로 오탐/미탐 가능. 근거 문장을 함께 표시해 사용자가 검증 가능하도록 함.
- **NFR-6 학습 친화적 구조**: V1/V2/공통 코어의 폴더 구조를 학습자가 한눈에 이해할 수 있도록 명확하고 자기설명적으로 구성(예: `shared-core/`, `v1-web-serverless/`, `v2-server/` 등 이름만으로 역할이 드러나게). 과도한 빌드 도구 복잡성보다 가독성 우선.
- **NFR-7 코어 재사용**: 파싱/판별 코어 로직은 V1(브라우저)과 V2(서버)가 동일 소스를 재사용하여 규칙 불일치를 방지.

## 9. 핵심 요구사항 요약

브라우저에서 판독문이 담긴 CSV/Excel을 업로드하면, `판독문` 행만 대상으로 한국어 규칙 기반으로 "추적 관찰 필요" 건을 판별하고, 진료과(`dept`)별로 대시보드와 표를 나누어 보여준다. 각 건은 대기/진행중/완료 진행 상태를 표기할 수 있다. 파싱/판별 코어는 공통 모듈로 두어 V1(서버리스, localStorage)과 V2(Node.js+TS 서버, DB, 다중 사용자)가 재사용한다. 폴더 구조는 학습자가 한눈에 이해할 수 있도록 명확하게 구성한다.
